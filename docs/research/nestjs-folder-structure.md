# Cấu trúc thư mục NestJS: dự án lớn làm thế nào, và SyncBoard nên làm gì

Ngày khảo sát: 2026-10-24. Mọi repo được đọc trực tiếp bằng `git clone --depth 1 --filter=blob:none` rồi `git ls-tree`. Link trong tài liệu được ghim theo commit nên vẫn trỏ đúng khi repo đổi về sau. Ký hiệu `[Sx]` trỏ tới mục **Nguồn** ở cuối.

## 1. Tài liệu chính thức NestJS khuyến nghị gì

| Chủ đề | Tài liệu nói gì (trích ngắn) | Nguồn |
|---|---|---|
| Module là đơn vị tổ chức | "Modules are the **recommended** way to organize your components." Feature module "keeps boundaries clear. This becomes more important as the application or team grows". | [S1] |
| Mỗi module một thư mục | "The project structure generated by the Nest CLI encourages the convention of keeping each module in its own dedicated directory." | [S2] |
| Cây mẫu trong docs | `src/cats/{dto/create-cat.dto.ts, interfaces/cat.interface.ts, cats.controller.ts, cats.module.ts, cats.service.ts}`, `app.module.ts`, `main.ts` ở `src/` | [S1] |
| Standard vs monorepo | Standard mode là mặc định, hợp với "individual, project-focused applications". Monorepo "may be more appropriate for teams of developers and/or multi-project environments". Có thể chuyển "at any time, so you can delay this decision". | [S3] |
| E2E test | "Keep your e2e test files inside the `test` directory. Test files should have an `.e2e-spec` suffix." | [S4] |
| Gateway là provider | "Gateways are providers: they can inject dependencies through the class constructor, and other classes (providers and controllers) can inject them." Nên dùng singleton, trừ khi thật sự cần state theo từng connection. | [S5] |
| Prisma | `prisma/schema.prisma` và `prisma/migrations/` ở gốc project. Client được generate vào `src/generated/prisma`. `src/prisma/prisma.service.ts` + `PrismaModule`, có thể đánh dấu `@Global()`. | [S6] |
| Config | `ConfigModule.forRoot({ isGlobal: true })`, file cấu hình nằm trong `config/`, validate bằng `validationSchema` (Zod/Standard Schema) hoặc hàm `validate()` trong `env.validation.ts` dùng class-validator. | [S7] |
| Circular dependency | "Avoid circular dependencies where possible". Không dùng barrel file (`index.ts`) cho class module/provider vì dễ gây vòng lặp import. | [S8] |

**Output thực tế của CLI** (đọc thẳng từ template, không qua docs):

- `nest new` sinh `src/{app.controller.ts, app.controller.spec.ts, app.module.ts, app.service.ts, main.ts}` và `test/app.e2e-spec.ts` [S9][S10].
- `nest g resource <name>` sinh thư mục `<name>/` chứa `<name>.module.ts`, `<name>.controller.ts` **hoặc** `<name>.gateway.ts` (tuỳ `--type rest|ws|graphql|microservice`; mỗi lần chỉ một loại), `<name>.service.ts`, các file `*.spec.ts` đặt cạnh, `dto/create-<singular>.dto.ts`, `dto/update-<singular>.dto.ts` và `entities/<singular>.entity.ts`. Tên file được chuẩn hoá về kebab-case [S11][S12].
- Template gateway inject service qua constructor (`constructor(private readonly xService: XService)`), tức là gateway → service [S13].
- Mẫu chính thức `sample/01-cats-app` có `src/common/{decorators,filters,guards,interceptors,middleware,pipes}` và `src/core/` (interceptor toàn cục). Unit spec đặt cạnh file, e2e nằm ở `e2e/` [S14]. Mẫu `02-gateways` đặt gateway trong `src/events/events.gateway.ts` + `events.module.ts`, Redis adapter ở `src/adapters/redis-io.adapter.ts` [S15]. Mẫu `22-graphql-prisma` có `prisma/schema.prisma` + `src/prisma/prisma.{module,service}.ts` [S16]. Mẫu `27-scheduling` đặt `@Cron` trong `src/tasks/tasks.service.ts` [S17].

Lưu ý thời điểm: docs đang viết cho NestJS v12 và Prisma ORM 7. Ví dụ dùng import ESM có đuôi `.js`. Docs cũng cảnh báo tag `latest` của `prisma` trên npm đang trỏ tới bản pre-release Prisma 8 [S6].

## 4. Cấu trúc đề xuất cho SyncBoard

Dùng standard mode, một app. Bộ khung gồm `common/ · config/ · infra/ · modules/`. Tên thư mục và file viết **số ít**, kebab-case. Lý do chọn số ít: đa số repo đã khảo sát dùng số ít, và tài liệu thiết kế cũng đã dùng `board/`, `asset/`. Lưu ý `nest g resource board` sinh route `@Controller('board')` [S12], nên cần sửa tay thành `'boards'` nếu muốn URL REST dạng số nhiều.

**Vì sao tách `infra/` (hạ tầng) khỏi `modules/` (nghiệp vụ):** đây là kiểu modular monolith có tầng hạ tầng riêng, và đã có tiền lệ:
- Twenty tách `engine/core-modules/` khỏi `modules/` [S18].
- Ghostfolio để Prisma, cron, queue và config trong `src/services/`, tách khỏi feature ở `src/app/` [S26].
- Cal.com gom feature vào `src/modules/` [S27].
- Một dự án NestJS nội bộ dùng để tham khảo (CRM chat đa kênh, không công khai) dùng đúng khuôn `src/{common,config,core/utils,infra,modules}`. Dự án đó có `socket-emitter.service` để module khác phát tin realtime mà không phải import gateway. Đánh giá dự án này chỉ dựa trên cây thư mục, chưa đọc code.

Không cần thêm các tầng `domain/application/infrastructure` cho mọi module. Chỉ `board/` có `domain/` cho phần logic thật.

**Các quyết định chính:**

- **DTO nằm trong `dto/` của từng feature, không có `src/dto/` chung.** Giống output của `nest g resource` và cách docs làm [S1][S11]. Thư mục DTO dùng chung sẽ thành "kho chung" bị mọi module import.
- **`board-locks.ts` nằm trong `board/`** vì chỉ board dùng nó. Hoppscotch cũng để guard riêng của team trong `team/guards/` [S29].
- **`board/domain/` chứa hàm thuần.** Đây là phần đáng lấy nhất của DDD: logic khó (LWW, z-index, quyền) test được mà không cần DB hay NestJS. Không cần repository, use case hay mapper cho mọi thứ.
- **Gateway tách sang `modules/realtime/`.** `board/` không phụ thuộc Socket.IO. REST và gateway cùng gọi `BoardService`.
- **`SocketEmitter` đặt ở `infra/socket/` và là module lá**, không import module nào. `BoardGateway` gán `Server` cho nó trong `afterInit`. Comment, snapshot, sharing muốn phát tin hay ngắt socket thì gọi emitter, nên không bao giờ sinh vòng phụ thuộc.
- **`sharing/` tách khỏi `board/`** vì hai lý do: gateway cần nó để tra vai trò khi `JoinBoard`, và nó cần emitter để ngắt socket khi thu hồi link.
- **Interface chỉ dùng ở chỗ đã biết chắc có ≥ 2 bản cài đặt.** Hiện chỉ có `infra/storage/` (ổ đĩa → S3/MinIO). Presence chuyển sang Redis (UC 8.4) thì thêm interface lúc đó.
- **Thư mục con theo vai trò** (`services/`, `controllers/`…) chỉ tạo khi một loại có từ 3 file trở lên. Trước đó để phẳng.

**Quy tắc phụ thuộc (một chiều, không vòng):**

```
BoardGateway (realtime) ──► BoardService, PresenceTracker, SharingService
BoardController ──► BoardService ──► domain/*, BoardLocks, PrismaService
CommentService / SnapshotService / ShareLinkService ──► SocketEmitter (infra, lá)
BoardGateway.afterInit(server) ──► SocketEmitter.bind(server)

Không module nào import RealtimeModule.   domain/ không import NestJS hay Prisma.
```

Chiều gateway → service khớp với template của CLI [S13]. Việc phát tin từ service đi qua một emitter lá, giống tinh thần Immich coi socket là adapter ra ngoài [S25], nhưng không tạo vòng. Phải dùng `forwardRef()` là dấu hiệu đã vi phạm quy tắc này [S8].

**Khi nào mới nên thêm "kiến trúc nặng" hơn:**

| Dấu hiệu | Thêm gì | Bằng chứng |
|---|---|---|
| Query Prisma giống nhau lặp ở nhiều service, hoặc unit test phải mock Prisma quá nhiều | `board.repository.ts` trong feature | Cal.com [S27] |
| Một service dài hơn khoảng 500 dòng với nhiều thao tác độc lập | Tách service theo nhóm thao tác (`operation.service.ts`) trước. Use-case-per-file chỉ dùng khi có rất nhiều thao tác | Novu [S21] |
| Cần process WS hoặc worker riêng để scale | Chuyển sang monorepo (`nest g app`), `apps/api`, `apps/ws`, lib dùng chung | Docs [S3], Novu [S20] |
| Hơn 50 module, nhiều team cùng làm | Tách `engine/` và `modules/` | Twenty [S18] |

Ở giai đoạn 1–4, SyncBoard chưa gặp dấu hiệu nào trong bảng trên.

## 5. Quy tắc áp dụng ngay từ ngày đầu

1. Một feature = một thư mục = một `*.module.ts`. Tạo bằng `nest g resource <tên>` hoặc `nest g module/service/gateway` để giữ đúng cách đặt tên của CLI.
2. Tên file kebab-case dạng `<name>.<type>.ts`, thư mục số ít. Không trộn với camelCase.
3. DTO nằm trong `dto/` của feature. Validate ở biên: `ValidationPipe` cho REST và cả `@MessageBody()` của gateway.
4. Code dùng riêng cho một feature thì để trong feature. Chỉ đưa lên `common/` khi đã có 2 module dùng.
5. Phụ thuộc chỉ chạy một chiều: gateway/controller → service → `infra/`. Không module nào import gateway; cần phát tin thì dùng `SocketEmitter`. `infra/` không chứa nghiệp vụ, `domain/` không import NestJS hay Prisma. Không dùng `forwardRef`.
6. Không dùng barrel `index.ts` cho module/provider [S8].
7. `ConfigModule.forRoot({ isGlobal: true, validate })` ngay từ GĐ1, để thiếu biến môi trường là app báo lỗi khi khởi động [S7].
8. `PrismaModule` khai báo `@Global()` một lần. Schema và migrations nằm ở `prisma/` gốc. Commit `migrations/`, không commit `src/generated/` [S6].
9. Unit test `*.spec.ts` đặt cạnh file. E2E `*.e2e-spec.ts` nằm trong `test/` [S4][S10].
10. Giữ standard mode cho tới khi thật sự có app thứ hai [S3].
